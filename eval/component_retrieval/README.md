# embedder/examples/eval — retrieval quality evaluation (BM25 vs BGE-M3 + RRF weighting)

The embedder's "quality gate": builds a retrieval evaluation benchmark from real corpus data, and the results
determine the sparse-model choice + RRF weighting. Run manually (GPU + Qwen3-VL + BGE-M3 models + real `parsed/`
data, not CI). Scripts assume `REPO` = the custodian repo root (relative to `__file__`); the engine package is
installed alongside custodian.

## Pipeline

```bash
python build_corpus_chunks.py   # select 14 documents -> chunk -> chunks.jsonl + programmatic exact-term queries queries_exact.jsonl
python select_semantic.py       # select semantic candidate chunks -> candidates.jsonl (an agent then generates queries_semantic.jsonl from these)
python index_eval.py            # index 1067 chunks into Qdrant: dense (Qwen3-VL) + bm25 + bge-m3, three vectors
python eval.py                  # #1 single-route recall comparison + #2 RRF weight sweep
```

- **Exact-term queries** (25): programmatically mine rare exact strings with df==1 in the corpus (`Section 6.1`/`CLEF-2021`/`$1196`/long IDs), golden = the chunk containing it. Tests sparse exact-match hits.
- **Semantic queries** (31): an agent reads a chunk and generates a natural-language question, **deliberately avoiding the original wording** (synonyms/paraphrase), golden = the corresponding chunk. Tests semantic recall.
- `chunks.jsonl` / `qdrant/` are generated by the scripts and gitignored, not checked in (regenerable); `queries_*.jsonl` are checked in (the semantic set was agent-generated and isn't reproducible).

## Conclusions

**#1 Single-route recall (MRR / Recall@10)**

| route | exact-term (25) | semantic (31) | overall (56) |
|---|---|---|---|
| bm25  | **0.738** / 0.96 | 0.210 / 0.45 | 0.446 |
| bgem3 | 0.584 / 0.88 | 0.347 / 0.61 | 0.453 |
| dense | 0.149 / 0.24 | **0.794** / 0.94 | 0.506 |

→ **Confirms the choice of BM25**: on the exact-term job sparse is supposed to handle, BM25 clearly beats BGE-M3
(0.738 vs 0.584); semantics is dense's job (0.794 crushes both sparse routes — BGE-M3's semantic advantage is
redundant within the hybrid); the two sparse routes are roughly tied overall, and BM25 needs zero model / zero GPU /
zero maintenance vs BGE-M3's 2.3G + GPU.

**#2 RRF weighting (dense + bm25, sweeping w_dense)**

| w_dense | 0.0 pure sparse | 0.4 | 0.5 equal weight | 1.0 pure dense |
|---|---|---|---|---|
| Overall MRR | 0.449 | **0.541** | 0.499 | 0.510 |

→ **Hybrid beats any single route** (peak 0.541 > pure dense 0.510 > pure sparse 0.449). Optimal w_dense≈0.4, but
this strongly depends on the exact:semantic ratio of the queries (≈1:1 in this set).
**Decision**: keep the store on Qdrant's standard RRF (equal weight, 0.499 is already close to the peak), don't
change the client-side weighting; principle: "don't set the sparse weight too low."

**Caveat**: synthetic evaluation set, small scale (56 queries), single golden chunk per semantic query (fair across
all three routes) → trends are trustworthy, absolute values are reference only.

## Gotcha

BGE-M3 auto-spawns a multiprocessing pool on multi-GPU machines; the spawned child processes re-import the script →
without `if __name__` protection this re-enters and hangs. The scripts in this directory are already protected with
`main()` + `if __name__=='__main__'`, and lock to a single card with `devices='cuda:0'`. See the repo memory
reference for details.
